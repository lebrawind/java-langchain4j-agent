## 二、主链路：一次请求的完整生命周期

1. **请求进门**：内嵌 Tomcat → `DispatcherServlet` → `RequestMappingHandlerAdapter` → `InvocableHandlerMethod` 反射调用 `AssistantController.chat`（断点栈里亲眼可见这串帧）
2. **接口的实现是谁**：`Assistant` 是接口，没有手写实现类。启动时 `AiServices.builder(...).build()` 用 **JDK 动态代理**生成实现类——断点里注入的字段实际类型是 `$Proxy66`。JDK 动态代理只能代理**接口**，这就是 Assistant 必须是接口的原因
3. **取记忆**：代理读 `@MemoryId` 参数值 → `ChatMemoryProvider` 创建 `MessageWindowChatMemory`（窗口 10 条）→ 底层调用我写的 `MysqlMemoryStore.getMessages()` 查 MySQL、反序列化 JSON
4. **拼请求发模型**：`SystemMessage`（来自 `@SystemMessage`，永远排第一）+ 历史消息 + 本次 `UserMessage` → `OpenAiChatModel`（baseUrl=DeepSeek）→ listener 的 `onRequest` 触发
5. **工具调用（Agent Loop 的最小形态）**：模型返回的不是文本，而是 `AiMessage{ text=null, toolExecutionRequests=[...] }` → 框架经 `ToolService.execute → DefaultToolExecutor.invokeMethod` 反射调用我的 `@Tool` 方法（中间经过 `executeWithErrorHandling` 层）→ 结果包装成 `ToolExecutionResultMessage` 回填 → **再调一次模型** → 第二次才产生文本答案
6. **回写记忆**：框架每往窗口加一条消息就触发一次我的 `updateMessages()`，把**整个窗口全量序列化成 JSON** UPSERT 进 MySQL

### 实测数据

- 普通请求：`updateMessages` 触发 **2 次**（用户消息 1 次 + AI 回复 1 次）
- 带工具调用的请求：触发 **4 次**（用户消息 → 带请求的 AiMessage → 工具结果 → 最终回复）
- 消息在窗口里的顺序：`System → User → Ai → User → Ai ...`

### ⚠️ 写放大

全量写库意味着：对话越长写的 JSON 越大、多用户并发时 UPSERT 有互相覆盖风险（last-write-wins）。**优化方向（待做）**：增量写 / 异步写。

## 三、注解点名表

**注册 vs 注入**：注册=把对象放进容器（@Component/@Bean/@Configuration），注入=从容器取出来塞给你（@Autowired/@Value）。一个是入库，一个是取货。

| 注解 | 体系 | 一句话 |
|---|---|---|
| `@SpringBootApplication` | Spring | 三合一：配置类 + 自动配置 + 组件扫描 |
| `@RestController` | Spring | 方法返回值直接写进 HTTP 响应体 |
| `@GetMapping` / `@RequestParam` | Spring | 路由 GET 请求 + URL 参数绑定 |
| `@Autowired` | Spring | 注入容器里的 Bean |
| `@Configuration` + `@Bean` | Spring | Java 版配置类；**方法返回值**注册为 Bean（构建过程要写代码时用） |
| `@Component` | Spring | 类上标注，启动时**扫描注册**（能直接创建的简单类用） |
| `@Value` | Spring | 注入配置值（同 @Autowired 一族），`@Value("${amap.key}")` 读环境变量 |
| `@SystemMessage` | LangChain4j | 系统提示，每次请求排最前（窗口 index 0，且**永不淘汰**） |
| `@UserMessage` / `@MemoryId` | LangChain4j | 本轮用户消息 / 参数值作为会话 ID 路由到对应记忆 |
| `@Tool` / `@P` | LangChain4j | 注册模型可调用的工具 / **工具参数的描述（给模型看的）**——曾把"北京"当默认值写进 @P，是 bug |

**踩过的 bug**：`@P("北京") String city` → `@P("要查询天气的城市名称") String city`。教训：`@P` 的值是给 LLM 的参数说明，写死一个城市会误导模型。

## 四、第 1 步：容错三件套（错误分类 + 重试 + 预算）

### 设计 

| 错误类型 | 判断标准 | 动作 |
|---|---|---|
| 瞬时错误（网络抖动、超时、QPS 限流） | **再试一次结果会变** | 重试 2 次、退避 1s→2s、总预算 15s；耗尽 → 回填模型 |
| 参数/业务错误（城市不存在） | 再试也没用，但模型可能换思路 | 回填模型（说清错在哪），让模型自愈或向用户澄清 |
| 永久错误（API Key 无效 401） | 谁来都没救 | 终止并报错 |
| 未知异常 | — | 框架 handler 兜底回填 |

**幂等性**：判断标准是"同一操作执行多次效果是否等于一次"，**不是**"是否碰数据库"。反例就在自己项目里：`ON DUPLICATE KEY UPDATE` 是幂等写（写库但可重试）；不碰库的"发短信"重试会重复发送。天气查询是纯读 → 重试安全（这条判断写进了代码注释）。

### 关键实现点

- 常量集中：`MAX_RETRIES=2`、`INITIAL_BACKOFF_MS=1000`、`RETRY_BUDGET_MS=15000`，不写魔数
- 退避用**重试计数器（attempt）**算，不是故障计数器——两个计数器混用是当时的 bug
- `Thread.sleep` 必须处理 `InterruptedException`：`Thread.currentThread().interrupt()` 恢复中断标志再退出（别人中断你是有意的）
- `TimeoutException` 是**受检异常**：方法内 throw+catch 齐了就不用声明 `throws`；没接住的必须声明
- 循环后加 `throw new IllegalStateException("unreachable")`——编译器无法证明循环必然 return/throw（只有 `while(true)` 有此豁免）
- 瞬时判定最终形态：`e instanceof TimeoutException || e instanceof ResourceAccessException`（RestClient 对一切网络层异常的包装）

### 对照实验

| 场景 | 无重试（基线） | 有重试 |
|---|---|---|
| 瞬时故障（读超时 1ms 强制复现） | 模型致歉"查询失败稍后再试" | 后台 3 次尝试+2 次退避，第 3 次成功，**用户无感** |
| 永久故障（Key 改错） | — | 无重试日志，模型收到原因后澄清 |
| 故障开关 | 临时脚手架（计数器字段），**验证完必须删** | — |

## 五、第 2 步：接入真实 API（高德）

### 架构

```
模型提取城市名 → getAdcode(city)【缓存→geocode 接口】→ adcode → 天气接口 → 解析拼句 → 返回模型
```

**分工原则：确定性的活交给代码，模糊的活交给模型。** 大模型会编造 adcode（小城市必翻车），所以转换必须代码做；模型只负责从自然语言里提取城市名。

- **adcode 缓存**：懒加载 cache-aside（第一次查接口、之后查表），`ConcurrentHashMap`（工具方法会被并发调用，HashMap 并发写有风险）
- **HTTP**：Spring 自带 `RestClient`（Boot 3.4 内置零依赖），URI 模板占位符 `{city}` **自动做 URL 编码**——URL 里有中文必须走模板，手动拼接会出编码问题；超时：连接 3s / 读取 5s
- **解析**：Jackson `readTree` + `path()`（字段缺失给默认值而不是空指针，比 `get` 适合解析外部数据）
- **返回给模型**：解析成干净中文句子（"北京今天多云，气温 7 度…"）而不是原始 JSON——原始 JSON 一次吃掉几百 token、暴露内部字段（`_float`）、失败 JSON 还会被模型当成功

### 先判成败，再取数据（重要！！！）

高德的业务错误**不抛 HTTP 错误码**——HTTP 200 + JSON 里 `status:"0"` + `info`/`infocode`。HTTP 层成功 ≠ 业务成功。

实测的错误形态（**外部 API 的错误形态要实测，不要想当然**）：

| 场景 | 返回 | 我代码走的分支 |
|---|---|---|
| Key 无效 | `status:0, info:INVALID_USER_KEY, infocode:10001` | status 分支 → ISE → 不重试 → 模型说明是配置问题 |
| 查不到的城市（阿特兰蒂斯） | `status:0, info:ENGINE_RESPONSE_DATA_ERROR, infocode:30001`（**不是 count=0！**） | status 分支 → 模型澄清 |
| 正常 | `status:1, infocode:10000, lives[0]{weather,temperature,winddirection,windpower,humidity}` | 拼句返回 |

如果只检查 count==0，"Key 无效"会被伪装成"城市不存在"，排查方向全偏——这是实测抓出来的真 bug。

### 异常是自己造的

外部 API 不主动给你 Java 异常。**你的代码解析响应后，把"坏结果"翻译成异常**：瞬时 → `TimeoutException`（喂给已写好的重试），永久 → `IllegalStateException`（交回模型）。重试体系一行不用改，等别人喂异常就行——这就是"按异常类型分类"设计的回报。

## 六、第 3 步：Context 管理

### 源码结论（`MessageWindowChatMemory.ensureCapacity`）

1. **截断时机**：`add()`/`messages()` 多处调用 → 每次追加时就裁剪，**MySQL 里存的就是裁剪后的窗口**（实测 updateMessages 收到的永远 ≤10）
2. **丢最老，System 豁免**：`if (messages.get(0) instanceof SystemMessage) messageToEvictIndex = 1` → 系统提示"永生"
3. **工具对保护**：淘汰指针遇到带 `toolExecutionRequests` 的 AiMessage 时，**请求和结果成对淘汰**（孤儿结果会让模型 API 报错）；遇到孤儿 ToolExecutionResultMessage 也会跳过

### 实验设计

同一 `memoryId` 连发 6 城（北京→上海→广州→深圳→成都）天气 + 1 次加法，观察 `updateMessages` 收到的条数变化 + 查库看 JSON 结构 + 最后问"第一次查的是哪个城市"。

### 两个发现

1. **工具对成对淘汰的指纹就是 10→9 抖动**——预言 1 的"差一"和预言 3 是同一个事实的两面
2. **滑动窗口的盲区：模型无法感知自己忘了什么**。被截断的历史不留痕迹，模型把残缺记忆当完整的、自信地答错（真实第一次是北京，它答深圳，因为窗口里剩的最老记录是深圳）。窗口开头甚至出现"没有用户提问的 AI 回答"（提问早被淘汰）

**启示**：按条数截断是粗糙代理（窗口里一半是几百字的长回答，10 条的 token 量波动巨大）→ 生产用**按 token 预算**；遗忘盲区 → **摘要记忆**（把淘汰内容压缩成摘要常驻）。这就是为什么企业级 Agent 不只用滑动窗口。

## 七、第 4 步：SSE 流式输出（11/9）

### 三角色

| 角色 | 作用 |
|---|---|
| `OpenAiStreamingChatModel` | 流式版模型：服务器边生成边推，框架每收到一段文本回调一次（Bean 装配与阻塞版完全相同） |
| `TokenStream` | LangChain4j 流式返回类型。Assistant 接口方法返回它 → AiServices **按返回类型路由**到流式模型（`String chat` 仍走阻塞模型，双模式并存）。三回调 `onPartialResponse`/`onCompleteResponse`/`onError` + `.start()` 启动 |
| `SseEmitter` | Spring 的 SSE 推送器：Controller 返回后连接保持打开，`send()` 推、`complete()` 收尾。**回调发生在后台线程，不是请求线程** |

### 设计决策

- 保留 `/chat` 同步版作对照组，新增 `/chat/stream`（同步/流式双模式并存）
- 错误处理：HTTP 头已发出就**不能再返回 500** → 错误作为一条 SSE 消息发出 + `completeWithError`
- 超时 120 秒（SseEmitter 构造参数；不设默认 30s，长回答会被腰斩）
- 参数校验在 return emitter **之前**直接 throw——此时响应未提交，走正常 400 路径

### 并发守卫（AtomicBoolean 原子操作实践）

`AtomicBoolean done`：`complete()` 之后不能再 send/complete（IllegalStateException），且 send 失败（IOException=用户中途关闭）后其他回调还会到达。用 **`getAndSet(true)`**——原子地"读旧值+置新值"一步完成，比 get-then-set 少一个竞态窗口。

### 实验与发现

- `curl -N`（-N 禁用缓冲）看到**词级 `data:` 逐段到达**（383 字节/3 秒）；同步版对照：卡 3 秒一次性吐全段。SSE 协议格式 `data: 内容\n\n` 可见
- **PowerShell 的 `curl` 是 Invoke-WebRequest 的别名**，不支持 -N：用 `curl.exe -N`（配 `chcp 65001` 防中文乱码）或换 Git Bash
- **记忆持久化验证——线程名实证**：`[nio-8080-exec-2]` 写第 1、2 条（请求线程：用户消息、System），`[onPool-worker-1]` 写第 3 条（流完成的回调线程：最终 AI 回复）→ 流式路径完整持久化记忆，且**亲手从日志线程名抓到了异步边界**
- **幻觉风险**：某轮窗口只有 3 条消息 = **工具根本没被调用**（工具轮应有 4~5 条 + 工具日志），模型把"晴，气温 5 度"直接编了出来 → **工具调用不是 100% 触发**，叠加第 3 步的"无感知遗忘"，构成流式 Agent 的幻觉风险面；强制触发：提示词点名"用天气工具查…"

## 八、第 5 步：RAG-lite

### 架构

- **离线**：`docs/*.md` → 按空行分块（>500 字按 400 硬切）→ 进程内 `bge-small-zh-v15` embedAll → 向量 JSON 存 MySQL `document_chunk`（实测 90 块）
- **在线**：问题 embed → 全量载入 → **手写余弦相似度**（点积÷模长乘积）→ Top3 → `ContentRetriever` → AiServices 自动注入提示词

### 关键实现点

- 依赖 `langchain4j-embeddings-bge-small-zh-v15`：进程内 ONNX 模型，**零 API 成本、免第三个 Key**；首次调用初始化几秒是正常现象
- `embedAll`/`embed` 返回 **`Response<T>` 信封**，`.content()` 拆包——照编译器报错读真实签名，教程可能过时（版本 API 漂移是常态）
- 手写余弦 + **除零防护**：零向量（空块/退化嵌入）才触发除零——"文本不相关"只是 cos≈0 合法值；不防护会 NaN/Infinity 混进排序且**不报错、悄悄乱序**
- `ContentRetriever` 版本差异：1.23 要求返回 `List<Content>`（`Content::from` 包装），不是旧教程的 `List<TextSegment>`
- **分块**：按空行切自然段，超长硬切 400 字；bge 单段上限 512 token（中文一字≈1 token）

### 实验结果（memoryId=user5）

1. "容错三件套怎么设计的" → 命中设计表格 + errorHandler 段落；模型主动指出"摘录没展开实现细节，建议核对源码"——**不编造，缺证据就明说**
2. "量子纠缠是什么" → 用自己知识正常回答，且明确声明"这是常识回答，不是依据资料"——没被无关检索块带偏
3. "滑动窗口的盲区" → 精准命中第 6 节两段 + 预言表

### 两个发现

1. **框架默认把"增强后的完整消息"（问题+检索块）存进记忆**——实测 inputToken 从 384→489→1078→1865 疯涨，10 条窗口只装了 3 轮对话。概念上证据不该进记忆（挤窗口/会过期/职责分离），**但默认实现是存的**——生产要自定义 RetrievalAugmentor 或明确接受这个代价。
2. **分块质量决定检索上限**：按空行切把 markdown 表格撕碎（截断的 `cuteWithErrorHandling`、孤行 `---`），导致模型抱怨"摘录没展开细节"——不是模型笨，是证据碎。生产解法：按标题层级切、表格整块保留、块间重叠。**这是 RAG 精度的第一杠杆。**

## 九、工程习惯

1. **本地 ≠ 仓库**：int 测试、30 条用例都在本地，git 里看不到——重要状态要进仓库
2. **Git 三条**：提交前 `git diff` 自检；一个逻辑改动一个 commit（曾把整个重试功能打包进标着"chore: 日志"的提交）；已 push 的历史不改写，错了补 commit
3. **改完代码必须重启**才生效（没有 devtools 热加载时）——"改了没生效"先查这个
4. **Debug 模式启动**断点才生效；调用栈面板取消"仅显示重要帧"能看到框架层
5. `Cannot resolve symbol` 九成是缺 import，Alt+Enter 一键修；但 Alt+Enter 给的候选要看包名（TimeoutException 曾错导成 langchain4j 的）
6. 受检异常：方法内 throw 且 catch 了就不必声明 throws；没 catch 的必须 throws
7. 编译器禁止 unreachable 代码；循环可能零次执行所以循环后需要保底 return/throw
8. 临时脚手架（故障开关、验证日志）**验证完必须删**，但先跑出"无重试基线"再做对照
9. 日志：System.out 换 slf4j（有时间戳/级别/可控）；**Key 等敏感值验证用长度不用值**；临时验证日志用完删或降 debug
